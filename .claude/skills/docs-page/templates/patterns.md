# MyST pattern library

Devices worth reusing across MNUtils docs pages. Reach for one only where it **carries the
argument**. A decision tree drawn as a flowchart is checkable at a glance; the same tree in prose
is not. Nothing decorative.

## Structuring the argument

| Job | Device |
|---|---|
| The whole design in one sentence | `:::{important}` |
| What you get, at a glance | contract table, input × output |
| What this page calls, at a glance | API-anchor table under the hook |
| Tiers that differ in cost | table with a cost column |
| A choice a contributor faces | `{mermaid}` decision tree |
| One call traced through every layer | `{mermaid}` flowchart TD |
| Guardrail, one-way door, footgun | `:::{warning}` + verbatim error |
| Hard prerequisite | `:::{seealso}` at the top |

### Linking into the API reference

`docs/api/` is generated by `uv run docs-api` and gitignored, but its MyST targets are
project-global, so any page can link one directly:

```markdown
| [`get_mat_data_from_series()`](#mnutils.utils.data_loaders.get_mat_data_from_series) | loads a raw series |
| [`GESeries.to_nifti()`](#mnutils.GESeries.GESeries.to_nifti) | converts to NIfTI |
```

Never guess: `grep -n "^(mnutils" docs/api/*.md` after `uv run docs-api`. A missed anchor renders
as literal text with no build error, so check the built page.

### Open on the reader's own question

State the objection as a blockquote and then follow it the whole way down, instead of announcing a
topic:

```markdown
> **Why does this only work for GE data?**

That single question shapes the whole vocabulary design. Let's follow it.
```

### Name the tempting wrong answer, then kill it

```markdown
❌ **The road not taken:** <the tempting shortcut>.
...
✅ **The rule:** <what MNUtils actually does, and why>.
```

### ❌ anti-pattern → ✅ solution, on the main line

This stays **on the main line** — it is pedagogy, not an appendix. The split is by *who* rejected
the option, matching the rule `dev-diary` uses:

- **The reader would naively try it** → paired ❌ / ✅ blocks, inline.
- **We considered and dropped it** → `:::{dropdown} Why not <X>?`, off the main line.

## Dropdowns — three distinct jobs

| Job |
|---|
| Background an expert skips, a beginner needs |
| Deliberation, with the issue linked for the full record |
| Boilerplate the reader should not have to scroll past |

The third is worth the habit: a long plotting helper inline pushes the actual point below the
fold.

## Math

LaTeX for the math **actually being demonstrated**, not for decoration. `$$…$$` display for the
equation the page is about, `$…$` inline for symbols in prose. Complexity claims read well in a
table cell: `$O(N \log N)$`.

## Mermaid

- **Always double-quote** node and edge labels: `A["label"]`, `B{"decision?"}`, `-->|"edge label"|`.
- **Line breaks inside labels: `<br>`**, never `\n`.
- **Code inside labels:** `<span style='font-family:monospace;'>GESeries.load(...)</span>` —
  markdown backticks do **not** render inside mermaid labels.
- **Single quotes** for HTML attributes and for literal quotes inside labels; never nest unescaped
  double quotes.
- Prefer the ```` ```{mermaid} ```` directive over bare ```` ```mermaid ```` fences — the checker
  warns on the bare form.

## Admonition syntax

Both `:::{note}` and ```` ```{note} ```` fence styles work; `:::` is preferred for anything
containing a code fence, since nesting backticks inside backticks is fragile. Write `:::{note}`
with no space after the colons.

A title goes on the opening line — `:::{note} Naming convention`. `:::{admonition} Custom title` +
`:class: warning` gives an arbitrary title on a styled box.
